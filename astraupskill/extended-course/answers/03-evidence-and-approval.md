# Answers: evidence and authority

The log predicate includes both time boundaries and filters on the primary service. The count covers all matching rows observed by the count query; the sample takes at most twenty IDs in descending timestamp order with an ID tie-break. A fixture must state whether boundary records are included in its advertised total before an expected count can be calculated correctly.

Separate count and sample queries can observe different populations under concurrent ingestion unless a stronger database observation contract is established. EF InMemory behavior does not prove a PostgreSQL snapshot guarantee. Late-arriving logs can also change a future replay of the same event-time window. Persisted sample identifiers help retain what the original investigation actually selected.

An authorized no-match investigation still creates a completed retrieval run, two recorded tools and a pending approval in the inspected method. Its output says modelUsed false and modelConfidence null. Completed describes workflow completion, not a solved incident. Unauthorized callers should create none of those records through this path, while a missing incident returns null before the evidence graph is constructed.

A provenance proposal should preserve a document version or retrievable snapshot, not just its mutable title. A digest detects changes but cannot reconstruct content by itself. Approval should bind to a defined recommendation and evidence version if the desired policy forbids stale approval of changed material. That policy must be implemented explicitly rather than inferred from a Pending status field.

The evidence-review worksheet separates observed facts, hypotheses, proposed actions and authority. A heuristic score belongs with retrieval facts. A cause hypothesis still requires incident evidence. A proposed runbook step still requires applicability review and whatever action authorization the product defines. Confusing those categories is a substantive failure even if every JSON field is present.
